The UI work, explained plainly

Why UI takes ten tries — and what we're building so it doesn't

A short version of the plan for anyone who isn't steeped in UX process. No jargon without a translation; the technical pages are linked at the end.

The problem

Software tests can't see the screen

When Claude builds a button, it writes a test that asks the code "is there a button here?" The code says yes. What the test can't ask is: does the button sit where it should, does clicking it do one thing and only that thing, can you get back afterwards, does the text fit? Those questions can only be answered by looking at the running app — and today the only one looking is you.

What this looked like in August

A collapsible project list in the AODex sidebar — "click a project to expand it" — took ten rounds of fix-and-look over four days. Every round passed its tests. Then a person looked: the chevron also selected the project; closing a group navigated away; the indent was wrong; a click landed on the whole row instead of the arrow. Each was found only after a build, a deploy to the test server, and someone clicking around. One whole session was spent testing against a bundle that was two weeks old without anyone realising.

Across the last four months, for every UI feature commit on AODex there was almost one fix commit. That is the tax this plan removes.

The idea

Write down how the screen should behave, once — then let a machine check it after every step

Today the description of how a screen works lives in your head and gets discovered one complaint at a time. The plan gives every screen a one-page written description that a person can read and a program can check:

  • Where can you be, and how do you get there and back? (every page has a way in and a way out)
  • What does each button do — and what must it never do? ("the chevron opens the list; it never navigates")
  • What does the screen look like when there's nothing, when there's a lot, when something is broken?
  • What resets when you switch company or workspace?

We're calling that page a Surface Spec ("surface" = one screen or feature area). It's the same thing a good product manager would write on a whiteboard — just in a form that tests can be generated from.

What changes for you

How building a screen will work once this ships

  1. You describe the feature, as now. If there's a mockup or the existing Trades screen, you point at it.
  2. Claude writes the one-page description and renders pictures of every state — normal, empty, long names, error, narrow window, dark mode — laid out on a single review page next to the mockup. It also draws the map of pages and arrows, so "can I get back from here?" is visible before any code exists.← this is where you spend your time
  3. You say yes, or comment. Comments get re-rendered in seconds (it's a picture of a component, not a deployed app). When you say yes, that page is locked and becomes the definition of "correct".
  4. Claude builds it, and after every step a program checks the real running app against the page: is every button there, does clicking it do what the page says and nothing else, can every page be reached and left, does the text fit, is the contrast readable, does keyboard use work. Failures are fixed by Claude without asking you.
  5. You look once more, only at what the machine couldn't judge — usually a short list, sometimes nothing.
  6. A crawler walks the whole app on every change and files a bug for every page nobody can reach, every dead end, every button that does nothing. Those become tickets, not surprises in a demo.
Today
  • Acceptance criteria discovered one complaint at a time
  • You are the only check for "does the screen work"
  • Every look costs a build and a deploy
  • Green tests while the screen is broken
  • Unreachable pages found by users
After
  • Acceptance written once, on a page you approve
  • A program checks the screen after every step
  • Your look costs a page refresh
  • A check that didn't run says "MISSING", never "pass"
  • Unreachable pages found by the crawler, filed as tickets

What it doesn't do

Honest limits

It doesn't replace your taste. Whether the indent looks right is still your call — the plan just asks you once, on a picture, instead of after every build. It doesn't make Trades pixel-identical — Trades is the checklist of what must exist, not what it should look like. Phones come last (wave 4). And one part is genuinely new infrastructure: neither app can currently fake a service outage, so "what does the screen say when a service is down?" can't be checked until wave 1c builds that.

Glossary

The jargon, translated

Surface Spec surface = one screen or feature area
The one-page description of how a screen works: pages and arrows, buttons and what they do, the states it can be in, what resets on a switch. Written by Claude, approved by you, checked by a program.
Look-lock
Your approval of the review page. After it, the pictures on that page are the definition of correct, and building starts.
Review sheet
The one page you approve: every state as a picture, beside the mockup, with the page map and a plain-language table of what each button does.
Probe
A small piece of code, only in test builds, that lets a program ask the running app "where is this button on screen, and what's under the mouse here?" Without it, tests can't see geometry.
Conform / checks
The after-every-step comparison of the running app against the Surface Spec: present, clickable, does the right thing, doesn't do the wrong thing, reachable, escapable, fits, readable, keyboard-usable.
MISSING
The verdict a check reports when it couldn't run. It is never allowed to be reported as "pass". This single rule is behind most of wave 0.
Judge
A vision model asked "list the differences between this screenshot and the approved picture". It only runs after the deterministic checks pass, and only with an approved picture to compare against.
Crawler / explorer
Two programs that walk the whole app: one follows the specs and reports every page that can't be reached or left; the other clicks everything with no script and reports dead ends and dead buttons. Both file tickets; neither changes code.
Pattern library
Written-down rules for things that recur — collapsible groups, empty states, forms, confirm dialogs — so every screen using them inherits the same behaviour instead of re-deciding it.
Wave
A batch of work that must finish before the next can start; each is one or two DevFlow objectives.
